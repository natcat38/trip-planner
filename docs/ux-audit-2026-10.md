# UX audit: trip-planner (ID prefix TRIP) (moved into the repo 2026-11-09)

The UX audit, its owner decisions and fix log, moved here from a local working folder so the record
lives with the code. Screenshot names in the findings refer to the original audit folder, which is
not kept; key before/after shots are in `ux-audit-2026-10/` beside this file.
The public-repo audit of the same period is in [`public-repo-audit-2026-10.md`](public-repo-audit-2026-10.md).

Audited at origin/main `c2e80d3`. Live shared trip plus the signed-in app run locally from a detached worktree (production build, seeded "Fukuoka in Autumn" trip, a session row created for the seed user `demo@example.com`; worktree, server and throwaway Postgres container removed afterwards). No edits, issues or PRs. No open issue covers any finding below (the only open issue, #56, is an e2e flake).

Measurements: `shoot.mjs` on the live shared page, re-run after the coordinator's smooth-scroll fix (5.2 screens desktop, 6.1 phone, nothing pinned; unchanged). The app sets no `scroll-behavior`, and a grep for `sticky`/`fixed` finds only the offline banner and the itinerary map pane, so the pinned-bar result for the signed-in pages stands. Signed-in numbers come from my own Playwright script at 1440x900, 390x844 and 320x700. Screenshots are in `UXP/shots/` (`tp-*.png`, `trip-shared-*.png`, `tp-audit.log`).

## Verdict

The shared view reads as one narrow 768px column on a 1440px screen. The budget card and a 576px map come first, so the itinerary starts 1.4 screens down on desktop (1016px, 1.2 screens, on phone). The map scrolls away, so you cannot see where a stop is while you read it, and there is no header, no day navigation and nothing pinned. The signed-in app already has the better design on desktop (itinerary beside a sticky map), but its trip page puts the budget form and the sharing panel before the itinerary, so the first day starts 1.2 screens down on desktop and 2 screens down on phone. The page is 9.7 screens on desktop and 13.5 on phone, with 272 Tab stops, and the header scrolls away. The biggest single win is to put the itinerary first and keep the map in view while reading it, on both views (Decisions D1 and D2), plus a sticky compact header (TRIP-UX-4, no decision needed).

Contrast passes everywhere I measured (lowest 4.59:1 for `text-zinc-500` and `text-danger` on the page background, so there is no headroom; muted text 4.56:1+, dark mode 7:1+). No horizontal scroll at 320px on the trip and places pages. Loading, error and 404 pages exist and are designed.

## Decisions for Natalie

**D1. How should the shared view lay out? (blocks TRIP-UX-1, 2; touches 3)**
It protects the page a recruiter sees first and decides whether it feels like a product or a document. The signed-in app already puts the map beside the itinerary on desktop; the shared view does not.
- A. Reuse the signed-in two-pane layout. Desktop: itinerary on the left, sticky map on the right, budget as a slim summary bar above with the breakdown collapsed; phone: budget bar, then itinerary, map behind a "Map" toggle. Trade-offs: consistent with the app and the least new design; the map competes with the itinerary for width and loses the full-width hero feel.
- B. Keep one column but make it a proper document: wider (about 1100px) with a sticky day-chip strip, budget collapsed into a summary bar, map as a full-width band that is sticky-small at the top of the viewport while reading. Trade-offs: closest to the current feel and cheapest; still scrolls 4-5 screens and the map takes vertical space.
- C. Tabs: Itinerary | Map | Budget, each fitting one or two screens. Trade-offs: shortest page and the first screen shows the itinerary; hides the budget (a selling point) behind a tap and changes the "scroll through the story" feel.
No option is wrong on a fact. All three leave the page under 3 screens for the primary view only if the budget breakdown is collapsed.

**D2. How should the signed-in trip page be organised? (blocks TRIP-UX-5, 15; shapes 10, 11)**
It protects the planner's main job (editing the itinerary) and decides how much of the page is reachable without scrolling. Today: budget, sharing, itinerary, checklist and attachments in one 9.7 / 13.5 screen scroll.
- A. Tabs on the trip page: Itinerary | Budget | Sharing and files (Checklist, Attachments), with the tab bar under the sticky header (top tabs on phone, or a bottom tab bar). Trade-offs: each view short, active-state and Back button can follow the route (`?tab=`); more navigation and a bigger change to how the page feels.
- B. Keep one page but reorder: itinerary and map first; budget as a collapsed summary bar that expands; Sharing, Checklist, Attachments as collapsible sections at the bottom. Trade-offs: smallest change, no new routes; still long (about 8 screens) and relies on collapsing.
- C. Desktop side column: budget summary and sharing in a left or right column beside the itinerary, with the map sticky above it; phone uses option B. Trade-offs: everything visible at once on desktop; the most layout work and a dense screen.

**D3. Identity and the recruiter path (blocks TRIP-UX-3, 14, 20; the OG image part of 19)**
It protects first impressions: a visitor currently sees no logo anywhere, a stock sign-in page and no preview card. This is branding and copy that makes claims, so it is yours.
- A. Text wordmark only: "Trip Planner" in the existing type (Geist) with the accent colour, used in the header, sign-in page and OG image. Trade-offs: no design time and consistent with the departure-board direction (ADR-0019); weak recognisability.
- B. Simple logo mark: a small mark (the favicon disc exists) plus wordmark, which you supply or approve. Trade-offs: better recognition in browser tabs and previews; needs a mark from you, and an agent must not invent one.
- C. Per-trip identity: the OG image and shared-page header are generated from the trip (name, dates, map thumbnail), with a small wordmark. Trade-offs: the best link preview for a shared trip and strong for a portfolio; the most work and needs a map-image source (Mapbox static images use the token).
Also decide whether the landing page and shared header carry a "View a sample trip" or "Plan your own trip" call to action, and the exact copy.
